## 3. What went wrong, how I investigated, and what confirmed the fix

### 1. The class's region wasn't allowed for my student account

- **What happened:** the class guide said to build the VM in the West US 2 region, but Azure wouldn't let me.
- **How I figured it out:** Azure for Students only lets you build in a few regions. My subscription has a rule called "Allowed resource deployment regions" that lists just five: West US, North Central US, Canada Central, Mexico Central and Sweden Central. West US 2 isn't on the list, so Azure blocked it before anything was created.
- **How I fixed it:** I built the VM in North Central US, which is on the list.
- **How I know it worked:** Azure shows the VM deployment as "Succeeded" on 9/24, and the VM's region is North Central US. The region only changes where the server physically sits, not how the app runs.

### 2. I first moved fake demo data, and the app would have brought it back

- **What happened:** when the app was first built, it filled its database with made-up "demo" content (three fake projects). My first migration copied that database to the VM. Every check passed, but a brand-new install would have shown the exact same fake content, so the checks couldn't prove my file had actually moved. On top of that, every time the app starts it runs a setup step that said "if any demo project is missing, add it back". So if I replaced the demo projects with my real ones, the next restart would have put the fake ones right back.
- **How I figured it out:** before putting in my real profile, we read the app's setup code and saw that rule.
- **How I fixed it:** test-first. We wrote a small automatic check that says "if the database already has real projects, starting the app must not add the demo ones". It failed, which proved the bug was real. Then we changed the rule to "only add demo projects if the table is completely empty", and the check passed (all 6 checks pass). The checks also run on a throwaway copy now, so they can never touch my real database.
- **How I know it worked:** after copying my updated database to the VM and restarting the app, the page showed my school email and my 4 real projects, and zero demo projects. The file's fingerprint (a code calculated from every byte, `f27e4d51…`) was identical on my laptop and the VM, so it's the exact same file. The fingerprint didn't change after the app started, so the setup step left my data alone, and the app's log showed it never used its backup file.

### 3. SSH froze when I tried to connect from home

- **What happened:** at home, my command to connect to the VM just hung and then timed out.
- **How I figured it out:** a freeze means something is blocking the connection, not that my login was wrong. My firewall rule only lets in my campus internet address, and at home my laptop has a different one, so Azure dropped the connection. (The VM was also turned off by the nightly auto-shutdown.)
- **How I fixed it:** back on campus, my address matched the rule again, so no change was needed. I started the VM and connected.
- **How I know it worked:** with the same rule, the connection worked right away on campus, which shows it was the firewall and not the VM.

### 4. Azure said my resource group didn't exist

- **What happened:** the first Azure command said it couldn't find `rg-career-platform`.
- **How I figured it out:** my Azure account has two subscriptions, and the command line was looking in the wrong one by default. The VM is in "Azure for Students".
- **How I fixed it:** we told every Azure command to use the "Azure for Students" subscription.
- **How I know it worked:** the same command then found the VM and showed its status.

### 5. The agent thought the app was running when it wasn't

- **What happened:** when starting the app, the agent's check said "already running" twice, but nothing was running.
- **How I figured it out:** the check looked for any program whose name mentioned the app, and it found its own command. We confirmed nothing was actually using port 8000.
- **How I fixed it:** the check now looks at whether something is using port 8000, which is what actually matters. The plan's stop command had the same flaw, so it was fixed the same way.
- **How I know it worked:** the app started normally, and every restart after that stopped and started cleanly.

### 6. The agent wrote something in my plan it hadn't checked

- **What happened:** the agent wrote that port 8000 had never been opened, but I had opened it for the two-locks exercise.
- **How I figured it out:** when my site's public address didn't load, the agent read the real firewall rules and saw the port 8000 rule I had made.
- **How I fixed it:** the plan was corrected, with a note explaining the mistake.
- **What I learned:** check the agent's claims against real output instead of trusting what the plan says.

## 4. The change

> You're at a coffee shop and try to SSH into your VM to fix a typo. The command hangs.

The SSH firewall rule only allows my campus IP address, and the coffee shop gives my laptop a different one, so Azure drops the connection and SSH hangs instead of saying "permission denied". I'd use the portal or `az`, which still work because they go through Azure and not port 22, to change the rule's source to the coffee shop's address with `/32` (never Any), fix the typo, and then switch the rule back. It costs a few minutes and a firewall change every time I'm on a new network, and while the rule is open, anyone sharing that Wi-Fi address could try to connect, although they'd still need my private key.
