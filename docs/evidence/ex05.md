# Exercise 05 evidence: investigate a DNS or TLS failure

## Setting and prediction

This is the **supplied simulation**, not my real system. The hostnames, IP addresses, commands and outputs below were invented for the lab and given to me in the assignment. I did not run any of them, and none of them are results from `chelseahuang.me`.

The setup: `site.lab.example` should reach a new Railway deployment. The Railway-provided URL already returns the current page and database content. Cloudflare is authoritative for `lab.example`, and the site's record is DNS only.

The failed check is `curl -Iv https://site.lab.example/`.

What I predicted should happen if everything were set up correctly:

- `dig site.lab.example A` leads to Railway, not to the old Azure address.
- `curl` connects to a Railway address, gets a certificate for `site.lab.example`, and returns an HTTP status line.

## Failed check and evidence

Simulated output, supplied by the assignment and read on 2026-10-13. I did not run these commands.

The zone before repair (simulated):

```
site.lab.example.  300  IN  A  198.51.100.24
```

The two checks (simulated):

```
$ dig site.lab.example A +noall +answer
site.lab.example.  300  IN  A  198.51.100.24

$ curl -Iv https://site.lab.example/
* Connected to site.lab.example (198.51.100.24) port 443
* Server certificate: subject: CN=old-vm.lab.example
* SSL: certificate subject name does not match target host name 'site.lab.example'
curl: (60) SSL certificate problem: certificate subject name does not match target host name
```

The actual result didn't match my prediction. DNS answered with the old Azure address, and `curl` stopped with error 60 before it sent any HTTP request.

## Diagnosis

Written before I opened the follow-up results.

**DNS to the destination.** `dig` returns `198.51.100.24`, which is the old Azure record still in the zone. DNS is working, because it answers with exactly what the zone contains. The record is just out of date, so the name still points at the old VM.

**TLS to the certificate.** `curl` connects to `198.51.100.24` on port 443, so the old VM is up and reachable. That VM sends its own certificate, for `old-vm.lab.example`. I asked for `site.lab.example`, the names don't match, and `curl` refuses to continue.

**Which fault came first.** The error appears at the TLS step, but the cause is one step earlier, in DNS. The stale A record sends me to the wrong server, and the wrong server correctly shows a certificate for its own name. The failed observation that supports this is the `Connected to site.lab.example (198.51.100.24)` line together with `CN=old-vm.lab.example`: the address is the old Azure one and the certificate belongs to the old VM, so I never reached Railway at all.

**What the evidence supports.** The app is not the problem, because the Railway URL already returns the right page and database content. The certificate on the old VM is not broken either. It is valid for its own name.

**What is still uncertain.**

- I haven't seen Railway serve `site.lab.example` yet, so I don't know that Railway has a certificate for that name. The ownership TXT record is verified, but that is not the same as an issued certificate.
- One `dig` answer comes from one resolver. Other resolvers could have a different cached answer.
- A correct DNS answer alone would not prove HTTPS or the database content works on the custom name.

## Repair and repeated check

**Proposed repair (written before the follow-up).** In Cloudflare, delete the A record `site.lab.example → 198.51.100.24` and add a CNAME record `site.lab.example → current-app.up.railway.app`, kept as DNS only. I would not change any certificate, and I would not use `curl -k` to skip the check, because that hides the error while still talking to the wrong server.

After the change I would wait out the 300 second TTL and then repeat the same two commands. I expect `dig` to show the CNAME to `current-app.up.railway.app` and a different address, and `curl` to show a certificate for `site.lab.example` and an HTTP status line.

**Repeated check (simulated follow-up).** This output was supplied by the assignment and read on 2026-10-13, after I wrote the diagnosis and proposal above. I interpreted it. I did not run it, and I did not make the DNS change myself.

```
$ dig site.lab.example A +noall +answer
site.lab.example.  300  IN  CNAME  current-app.up.railway.app.
current-app.up.railway.app.  300  IN  A  203.0.113.44

$ curl -Iv https://site.lab.example/
* Connected to site.lab.example (203.0.113.44) port 443
* Server certificate: subject: CN=site.lab.example
* SSL certificate verify ok.
< HTTP/2 200
```

| | Before | After |
|---|---|---|
| DNS answer | `A 198.51.100.24` | `CNAME current-app.up.railway.app.`, then `A 203.0.113.44` |
| Connected address | `198.51.100.24` (old Azure VM) | `203.0.113.44` (Railway) |
| Certificate name | `CN=old-vm.lab.example` | `CN=site.lab.example` |
| Result | `curl: (60)`, no HTTP request sent | `SSL certificate verify ok`, `HTTP/2 200` |

**The record change.** The A record for `site.lab.example` was replaced with a CNAME to `current-app.up.railway.app`. That is the same change I proposed.

**Which fault occurred first.** DNS. Only the DNS record changed, and the certificate error went away with it. Nothing was done to a certificate. Once the name led to Railway, Railway presented a certificate for `site.lab.example` and the check passed.

**Does this support my first diagnosis?** Yes, I don't need to revise it. It also settles one thing I listed as uncertain: Railway does have a certificate for the custom name.

**What this still doesn't show.**

- `HTTP/2 200` with `-I` is only the headers. It shows the server answered, not that the page has the current database content. I would load the page and compare it with the Railway URL.
- This is one resolver's answer. In a real cutover, other resolvers could keep the old address for up to the 300 second TTL, so I would repeat the check later and from another network.

## What you learned

The place where an error shows up is not always the place where it started. Here the error message was about a certificate, but the cause was a DNS record.

One other check that would separate a DNS problem from a TLS or application problem is to skip DNS for one request and send it straight to Railway:

```
curl -Iv --connect-to site.lab.example:443:current-app.up.railway.app:443 https://site.lab.example/
```

This still asks for `site.lab.example`, so the certificate check and the HTTP request are the same as before. Only the destination changes. I have not run this. It is the check I would add.

- If it returns a certificate for `site.lab.example` and an HTTP status line, Railway is ready and DNS was the only problem.
- If it still fails with a certificate name error, the problem is TLS on the Railway side: Railway has not issued a certificate for the custom name yet.
- If the certificate is fine but the response is a 404 or a 5xx, the problem is the application or Railway's routing for that hostname.
